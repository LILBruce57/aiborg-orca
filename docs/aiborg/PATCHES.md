Renderer notes:

- The wizard's setup commands (`ssh-keygen`, `gh auth login --insecure-storage`, `claude`, `codex login`, `aws configure sso`, `az login`, `gcloud auth login`) run in a floating terminal. Floating terminals are pinned to the active profile at spawn, so the wizard activates the new profile first and main binds the PTY. With the floating terminal off, the command can be copied instead.
- Secrets typed or imported in Settings only travel renderer → main → OS keychain; nothing is read back.
- Repo → profile in the renderer uses `repoBindings` and `boundRepoIds`, and for repos without a binding the main-side org match through `resolveRepoProfile({ repoId })` (binding, else the owners of its remotes, `origin` first; never the active profile). Those matches are dropped only when profiles, orgs or bindings change, not on every terminal open/close.

Main-process notes:

- **Personal mode is untouched.** With no profiles directory configured every hook returns its input unchanged, whatever `repoBindings` or `ptyBindings` the sidecar still holds.
- **Decisions:** WSL and orcad profile-bound spawns are refused in v1; SSH spawns only with `remote.allow`; no per-profile OS SSH host alias; the `helper =` reset stays (not `GIT_CONFIG_NOSYSTEM`).
- **Owner lookup** reads the repo's git config file (no git spawn on main), re-reading it when its mtime changes; only a config with insteadOf aliases or includes is refined by an async `git remote -v`. A repo whose remotes name an org of a profile file that fails to load, or of two profiles, is refused, not handed to the personal account. Worktrees Orca did not create are matched by their git common dir. Keychain reads are cached in memory for 15 s (hits only) because Orca's own git polls per worktree; a secret change, activation or delete drops the cache.
- **Secret status for the renderer** is cached per profile and refreshed only on secret changes, activation or a profile-file change, so terminal open/close broadcasts read no keychain entries; sidecar change broadcasts are coalesced.
- **Refusals** are audited as `terminal.refused` (at most one line per profile, action and reason per minute) or `structured.refused`.
- **gh logins** from the wizard use `--insecure-storage`: gh keys its keyring entry by host only, so a keyring login would be shared by every `GH_CONFIG_DIR` (all profiles and the personal one). The token then lives in `P/gh/hosts.yml`, which the delete flow wipes.
- **Known gaps:** `gitExecFileAsyncBuffer` (`git show` blob reads) gets no profile env; other agents' hook files (Gemini, Cursor, …) stay under the home directory; the AWS CLI's SSO and CLI token caches (`~/.aws/sso/cache`, `~/.aws/cli/cache`) are always in the real home, so AWS SSO is not isolated per profile and survives a delete (the wizard and revoke checklist say so); a Codex `cli_auth_credentials_store = keyring` login is not removed on delete (Codex's default file store is in `P/codex`); `pushInsteadOf` covers the common URL spellings (plain, `git@`/`x-access-token@`/`oauth2@` userinfo, `:22`, `ssh.github.com`), while other userinfo, IP hosts and SSH host aliases rely on the pre-push hook and the app-level guard, which `--no-verify` skips for the hook only; a stale `ptyBindings` entry is dropped when its session is next spawned and found dead, not at startup.

## 4. Decisions

- **appId** `be.aiborg.desktop`. It also sets the NSIS uninstall GUID and the Windows AppUserModelID. Fix it before the first keychain secret is stored (design §9).
- **Install folder / userData:** `%LOCALAPPDATA%\Programs\aiborg`, `%APPDATA%\aiborg` (macOS `~/Library/Application Support/aiborg`). Dev builds keep upstream's `orca-dev` userData, because the CLI's dev-mode detection keys on that name; dev never registers a global command (H14).
- **Daemon:** the named pipe is hashed from the userData runtime dir, so it already differs from stock Orca's; only the relocated host folder needed H5.
- **Protocol:** `aiborg://` only. Upstream registers no protocol client at runtime; `orca://` pairing strings are parsed as text and unaffected.
- **Executable / CLI name:** Windows keeps `Orca.exe` and the CLI stays `orca`, because the native launcher (`native/windows-cli-launcher/src/main.rs`) and daemon-host relocation resolve those names, and renaming them means rebuilding native code. Collisions are prevented instead: AI-Borg never registers or removes `orca` globally (H14-H16); inside AI-Borg terminals the app prepends its own `resources/bin` and sets `ORCA_USER_DATA_PATH`, so `orca` there talks to AI-Borg, while the `orca` on the user PATH keeps talking to stock Orca. The installer's running-app check is path-scoped and fails closed (H6). macOS ships `AI-Borg.app` with executable `MacOS/AI-Borg`, served by the launcher copy above.
- **Updates:** off (H8-H10, `publish: null`). No AI-Borg feed exists yet.
- **Telemetry:** off in two ways (H11 and `ORCA_TELEMETRY_DISABLED=1`). The fork never sets `ORCA_POSTHOG_WRITE_KEY` / `ORCA_BUILD_IDENTITY` either. Local crash breadcrumbs and logs stay on.
- **Plugin kill list stays on.** `onorca.dev/plugins/kill-list.json` is fetched only by a packaged app with the opt-in `pluginSystemEnabled` setting on (`main-process-plugins.ts:105`, `:133`); `initialize()` at `:36` reads the local cache only. It carries no client data, and turning it off while plugins run would drop upstream's plugin revocations.
- **`~/.orca/agent-hooks` stays shared on purpose.** Upstream already shares this path between prod, dev and parallel builds of different commits (`installer-utils.ts:106`), so the scripts are written to tolerate a writer at another version. A per-brand root would put a second managed hook entry into every agent config (`~/.claude/settings.json`, Codex homes) and double-post every status event. Mitigation: AI-Borg rebases on upstream monthly, so the version gap with an auto-updating stock Orca stays about a month; Phase 2 moves AI-Borg's agents to per-profile config homes.
- **`~/.orca-remote/` on SSH hosts stays shared.** A stock Orca and AI-Borg at different versions on one host behave like two Orca clients at different versions, which upstream supports by design (versioned relay dirs, `remote-install-coexistence.ts`, the remote-wire compatibility rules). The name is hardcoded in about 20 places, including the relay itself and remote shell scripts, so renaming it is a Phase 2 item if a conflict ever shows up.
- **NOTICE stays at the repo root.** Upstream's root-directory guard (`.github/scripts/check-root-directory-entries.mjs`, run in `pr.yml`) fails a PR that adds a root entry. Fork Actions are disabled and nothing from this fork is proposed upstream, so the guard never runs here.
